# herdr 0.9.5, and pinned dependencies

Date: 2026-10-22
Status: decided

## The decision

Kingshand moves from herdr 0.8.2 (protocol 20) to herdr 0.9.5 (protocol 22). Every behaviour
`bin\Herdr.psm1` depends on was re-measured against 0.9.5 with real workers, and all of them held.
The one change the module needed is for the moment the binary is swapped: a binary and a running
server on different protocols now fail loudly instead of reading as an empty fleet.

At the same time every dependency kingshand runs on gets a pin. `dependencies.json` at the repo root
records the exact version each release was verified with, `install.ps1 -SyncPins` moves a machine
to it, and `/update` runs that sync after it fast-forwards. A weekly, read-only report tells a
maintainer what has been published since.

## How 0.9.5 was measured without touching the live server

The live server was hosting workers, so nothing could be measured against it. 0.9.5 ran as a second
server from a scratch directory, under a named session of its own.

- `herdr --session <name> server` starts a server on its own socket, under
  `%APPDATA%\herdr\sessions\<name>\`.
- `HERDR_SOCKET_PATH` pointed at that socket routes an unmodified client to it, which is what let
  `bin\Herdr.psm1` run unchanged against the test server.
- `HERDR_SESSION` and `HERDR_HOME` do **not** isolate a client. With both set, `status` still
  reached the default server's socket. Use `--session` or `HERDR_SOCKET_PATH`, and check
  `status --json` names the socket you meant before anything else runs.
- A named server still shares the agent-detection manifests under `%LOCALAPPDATA%\herdr\`. 0.9.5
  added manifests for agents 0.8.2 does not know and left the Claude Code one as it was.

The same method, with a copy of the 0.8.2 binary under a second named session, is how both versions
and both directions of the mismatch were measured. A pin bump re-runs it.

## What held and what changed

Same on 0.9.5, measured with real workers:

- `workspace create` hands back `root_pane.pane_id`; `pane list` and `agent get` keep every field
  the module reads. 0.9.5 adds `completion_seq` and `launch_pending` beside them.
- A fresh directory stops on the folder-trust dialog; `agent start` exits 1 with `agent_not_ready`
  while the agent is registered and `blocked`, so the re-read stays right.
- `idle`, `working`, `done` (an unfocused pane whose turn ended) and `blocked` all classify as
  before. A question menu reads `blocked` from herdr and from the screen guard alike.
- The prompt box is still the caret and a no-break space; a menu row is still the caret and a plain
  space. A bare Enter on typed text is still refused.
- At 12 columns the screen guard is still blind and `Test-HerdrAgentReadable` still says so; herdr
  itself still calls that blocked worker `idle`. Closing the sibling panes still does not reflow it.
- `agent prompt` to a blocked worker still answers `agent_blocked`. A wait still times out with
  `timeout`, and an unknown name still answers `agent_not_found` with exit 1.
- `/exit` after one Escape still stops a worker sitting on a menu; closing a workspace's only pane
  from the command line does not ask first.
- `status --json` for a server that is not running exits 0 with `running` false. That was never
  measured before; the module already read the payload ahead of the exit code.

Changed, with no code needed: the free-text option reads `Type something.` with a full stop, which
the guard still matches; and `agent send-keys <name> down enter` in one call chose the right option
once, where 0.8.2 chose the wrong one. One success is not proof, so keys still go one per call.

## The mismatch, which is the one thing that had to change

When the binary and the running server speak different protocols, every command answers
`protocol_mismatch` and every pane keeps running. That was measured both ways between 0.8.2 and
0.9.5. Handed back as an ordinary error, it read exactly like "no such agent": a live worker read as
gone, a teardown reported a running worker stopped, and a progress wait called it gone. The binary
is swapped by hand after this lands, so that state is guaranteed to happen at least once.

So `bin\Herdr.psm1` throws `protocol_mismatch` from every reader, whatever the caller asked for, and
`Get-HerdrServerState` reports `compatible` from herdr's own answer. Nothing else in the module
needed to move, and 0.8.2 keeps working, so either binary can sit under this code.

## Pinned dependencies

`dependencies.json` is JSON because `ConvertFrom-Json` already reads it. Every installed version is
read from the tool that owns it - npm's JSON, herdr's `status --json`, and the one version line the
review gate and Claude Code each print - and a version that cannot be read stays unreadable rather
than being taken for current.

- **A pin is exact, and a sync never goes past it.** A newer version published since is the
  maintainers' to verify; a user's machine follows the release they are on.
- **Claude Code gets a minimum, not a pin.** It updates itself, and fighting that would mean
  downgrading the tool every worker runs in.
- **Only what the installer owns is moved.** npm globals, and the copies under this installation's
  own `tools\`. A herdr or review gate the user put on PATH is reported with the command and left
  alone, and so is a copy under another installation's `tools\`.
- **herdr is never replaced under a running server.** That is the mismatch above, created on
  purpose. A running server, or one whose state cannot be read, is a refusal that says to stop the
  server once no worker needs it.
- **herdr's download is checked against the pin and against latest.json.** latest.json now carries
  a `releases` map keyed by version, so the pinned version is fetched even after a newer one ships;
  a digest the two records disagree on is refused.

One defect turned up on the way and is fixed with it: a Node version manager's `npm.ps1` shim
answered `& npm ls` with `Unknown command: "pm"`. npm is now run through `npm.cmd` where it exists.

## The weekly refresh

`bin\Update-DependencyPins.ps1` lists, for every pin, the pinned version, the latest published one,
and whether the move crosses a breaking line - a herdr protocol change, or a change in the leftmost
non-zero part of the version, which on a 0.x line is the minor. Run plainly it writes nothing;
`-Record` also records that the weekly check ran, and the script's header owns that record. The
`statute` skill owns the procedure that acts on it.
